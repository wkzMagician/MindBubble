# 自适应推荐与模型接入

首页和系统通知通过 `RecommendationService` 使用同一个
`RecommendationEngine`。没有按笔记固定的提醒间隔，也不再使用每日推荐缓存。
每轮执行百分位排名、直接偏好、相似偏好泛化、时间恢复、语义多样性与探索混合，
再逐条无放回采样。所有推荐计算均在本地执行。

## 数据与迁移

Markdown JSON front matter 保持 schemaVersion 2，添加可选的 `noteProfile`
和 `recommendationState`，原有文件可以直接读取。初始属性包括
`cue_value`、`detail_need`、`cue_text`、`summary`、`embedding` 与向量模型标识。
不同模型或维数的向量不会参与相似度计算。

旧笔记没有分析属性时，把原有 1–5 档频率线性映射成 0–1 的初始提醒价值；
偏好为 0，推荐默认启用，不会为了迁移自动调用模型。
用户可在详情的“推荐属性”中修改数值、标题、摘要、向量、偏好和推荐开关，
也可以主动重新分析。停止提醒不会删除笔记，仍可在笔记列表中检索和重新启用。

展示次数和最后展示时间继续按设备保存，首页和通知共用这一状态。
行为记录位于应用支持目录的 `recommendation-events.jsonl`，包括展示、打开、
阅读、检索访问和明确反馈。发送回执按事件 ID 去重，迟到回执不会使最后展示时间倒退。
行为日志属于本设备，笔记属性与各设备曝光汇总随原有 Markdown 同步机制同步。

## 推荐与学习

实现使用设计文档的参数默认值：温度 0.4、探索比例 0.15、多样性强度 0.4、
反馈步长 0.15、泛化强度 0.2。首页数量仍为 5–10，通知每次可选 1–10 条，
通知计划继续使用现有间隔和免打扰设置。设置中增加推荐参数和效果统计入口。
首页数量与算法参数共用 `RecommendationConfig`，兼容读取旧的首页数量设置；
原有通知计划设置继续管理呈现时间与免打扰。

`B` 是最近 14 天实际展示的笔记数除以 14；未来计划和正文打开不计入。
`tau = N / max(B, 1)`，时间单位为天。每轮先固定候选集合的百分位、偏好与恢复系数，
再随着已选集合更新多样性及两个归一化概率分量。指数计算先减去最大对数权重，
避免小温度造成数值溢出。无反馈时跳过偏好传播的相似度计算；有反馈时也只为
非零传播分子计算完整平滑分母。

“多提醒/少提醒”更新并截断偏好到 [-0.6, 0.6]，“频率合适”只确认当前偏好，
“停止提醒”关闭推荐。打开正文不改变提醒价值或偏好。阅读只在前台计时，
不足 8 秒不学习；有证据时以 0.03 的学习率缓慢更新 `detail_need`。
摘要在 `detail_need >= 0.5` 时显示，提醒标题始终显示，正文通过详情打开。

统计包括频率反馈及正负比例、覆盖率、曝光分布、重复间隔、可比较向量的批次内
平均相似度、正文打开/阅读时间、检索访问，以及通知渠道的反馈分布。

## 模型模块

通用能力位于相邻 Dartloom 仓库的两个普通包中：

- `packages/dartloom_model`：`GenerationModel`、`EmbeddingModel`、请求和连接配置。
- `packages/dartloom_model_io`：OpenAI 兼容 API、桌面 Codex 订阅 CLI、本地 Ollama。

MindBubble 用路径依赖接入这两个尚未发布的包，应用配置目录同时记录包选择。
模型提示词、笔记输出验证及批量分析属于 `lib/features/recommendations`，
设置属于 `lib/features/model_settings`。没有新增运行时注册中心或生成 bootstrap 层。

API 模式填写兼容 Chat Completions 的服务根地址（如带 `/v1` 的地址）和模型名；
凭据由用户日后在设置中填写，保存到 Dartloom 的系统安全存储，并按服务地址隔离。
凭据不进入连接配置、Markdown、行为日志或同步内容。

订阅模式调用已安装并登录的 Codex CLI，复用 CLI 自身的订阅登录，不读取订阅令牌。
只支持桌面平台；运行环境仍须允许启动该 CLI 并访问其登录配置。
先检查 CLI 使用 ChatGPT 订阅登录，再通过 stdin 传入提示，在临时目录中执行
`codex exec --sandbox read-only --json`。关闭用户配置、项目说明、Shell、图像工具、MCP 和网页搜索，
采用不持久化会话的模式；需要支持这些配置选项的当前版本 CLI。
订阅不等同于 API 凭据，实际可用性取决于用户的 CLI 安装和账户权益。
协议依据官方文档：
https://developers.openai.com/codex/noninteractive 和 https://developers.openai.com/codex/auth 。

本地模式连接用户自己启动的 Ollama，生成使用 `/api/chat`，向量使用 `/api/embed`。
模型名称由用户指定，应用不会自动下载模型。Embedding 始终使用单独配置的本地服务，
支持批量请求。手机上 `127.0.0.1` 指手机本身；Android 模拟器可用 `10.0.2.2`
访问宿主服务，真机连接其他设备应配置 HTTPS 本地服务地址。

新建笔记自动分析一次；导入按每批最多 16 条生成一个请求，并批量生成向量。
编辑保留现有分析。未配置或模型不可用时保留笔记和既有属性，标记为待分析/失败；
不会在刷新、通知、编辑或启动时自动重试。用户可主动重新分析。
只有生成成功但尚无向量时，标记为 `embedding_pending`；推荐仍可工作，语义能力
在向量生成后生效。响应中的未知 ID、重复 ID、缺失记录和非法数值会拒绝应用。

## 实际展示与移动端限制

首页在当前路由的内容完成呈现后记录一次曝光；重绘动画不会增加次数，
被其他页面覆盖时不计曝光。桌面通知使用同一个推荐服务，每条窗口成功发送后记录，
多条提醒按展示时长依次呈现。

Android/iOS 由系统调度本地通知。未来通知使用同一数值引擎逐批规划，
在内存中模拟此前计划的曝光，绝不提前写入真实曝光次数。收到原生发送回执后，
才将事件及状态写入共同历史；回执确认成功后再从原生待确认队列删除。
应用恢复、笔记/偏好变化、推荐配置变化、首页曝光后重建移动端计划。

系统本地通知无法在应用被挂起时任意运行 Dart 推荐。因此挂起期间使用最近生成的
48 条通知计划；应用恢复后结合实际历史重新计算。队列耗尽后需要应用再次运行才能补充。
Android 在广播发送通知后持久化回执。iOS 在前台呈现、用户打开以及恢复时查询
仍存在于通知中心的已发送通知；被用户清除且应用从未观察到的通知，iOS 不提供完整
历史，可能漏计。系统权限、专注模式及厂商限制也会影响实际可见性。

## 验证

应用使用 `dart format .`、`flutter analyze` 和 `flutter test` 验证。
测试覆盖公式、稀疏反馈、批量分析、编辑不调用模型、双渠道状态、曝光回执去重、
迟到事件、阅读学习、日志损坏恢复、凭据隔离及设置/反馈界面。
Dartloom 两个新包分别运行 `dart analyze` 和 `dart test`；HTTP 测试使用本机回环服务，
不需要真实凭据，也不调用付费模型。原生通知和订阅登录仍需在目标平台实机验收。
